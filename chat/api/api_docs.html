Cancri API 文档

部署在Cloudflare Worker 上的统一模型网关，提例OpenAI Chat Completions　 OpenAI Responses 一Anthropic Messages 三条兼容路径。第三方工具能否接入！ 取决于它是否允许自定久Base URL、API Key 和模型ID　

概述

Cancri API 在一个端点后面统一了GPT、Claude、Gemini、DeepSeek、GLM　 Qwen 等模型，同一技Key，三种协计。优先选择客户端原生支持的 协议；IDE/Agent 的厂商托管模式不会自动继承这个自定义网关　

路径 协议 适合的客户端
POST /v1/chat/completions OpenAI Chat Completions openai SDK、LangChain、LiteLLM、OpenCode 等
POST /v1/responses OpenAI Responses Codex CLI（默认协议）
POST /v1/messages Anthropic Messages Claude Code、@anthropic-ai/sdk、OpenClaw
POST /v1/messages/count_tokens Anthropic Token Counting Claude Code 内部（auto-compact）；免费、不计配预
GET /v1/models OpenAI / Anthropic 自适应 带 anthropic-version header 时返回Anthropic 格式
Base URL： https://chat.nexusvai.xyz/functions/v1/api-gateway
公开入口：第三方客户端只需要配置本額Base URL、自己的 cancri_sk_ Key 与模型ID。模型路由、鉴权、配额和用量统计 由平台在服务端完成；调用方不需要配置上游线路、代理服务、数据库地址或内部管理端点　
Base URL 不能混用：OpenAI-compatible SDK / 工具塔 https://chat.nexusvai.xyz/functions/v1/api-gateway/v1！ Anthropic SDK / Claude Code 塔 https://chat.nexusvai.xyz/functions/v1/api-gateway　 原始 curl 示例则写完整路径　
  • 认证：Authorization: Bearer cancri_sk_xxx 或 x-api-key: cancri_sk_xxx
  • 支持流式（SSE）和非流式两种模式
  • 所有模型在 模型广场 可见
  • 图像 / 视频生成只在网页版开放，一对外 API 暴露
稳定的模型ID 你看到的 model 字段（如 gpt-5.4、deepseek-v4-pro、claude-sonnet-4-6！ 昂Cancri 维护的稳定品片ID。后端会自动负载均衡与故障切换， 调用方不需要感知具体路用，也不需要为故障切换调整 model 字段　

认证

推理请求需要带公开 API Key。网关接受两种等价认证头！ Authorization: Bearer cancri_sk_xxx 成 x-api-key: cancri_sk_xxx。Key 形如！

cancri_sk_48 一base64url 字符

前缀 cancri_sk_！0 字符！ 36 字节随机熵的 base64url 编码！8 字符！ 总长度恒一58 字符　 后半部分字符集为 A-Z a-z 0-9 - _（不吃+ / = 填充符）　 假Key 正则校验的客户端推荐用/^cancri_sk_[A-Za-z0-9_-]{48}$/　

  1. 刀申请額 提交申请
  2. 审核通过后到 Keys 管理額 生成 Key
  3. 技Key 安全存好（生成后只显示一次）
⚠️ 不要在浏览器代码或开源仓库里硬编码Key Key 一旦泄露， 立刻到 Keys 管理页撤销并重新生成　
公开 API Key 不是登录会话 cancri_sk_ Key 只用了 /v1/* 公开 API；网页版登录和站内账户功能使用用户会话， 二者不能互换　

你可以生成任意数量的 Key，但建议按需创建，过处Key 会增加管理复杂度

易混淆点

  • /v1/models 成功不代表写接口开放 维护闸门开启时，模型列表仍可读，/v1/chat/completions、/v1/messages、/v1/responses 会返回503 api_paused
  • 只使用公开 Base URL 公开客户端只调用本页 Base URL；其它地址不属于公开 API 合约
  • 模型 ID 用Cancri Canonical ID model 必须来自 模型广场 或 /v1/models 返回值，不要照搬上游官方 ID
  • OpenAI Base URL 布/v1，Anthropic Base URL 不带 Anthropic SDK 和Claude Code 会自行拼 /v1/messages、/v1/messages/count_tokens
  • 兼容协议不是完整上游平台能力 这里支持核心对话、流式、token usage 与自定义 function tools；OpenAI hosted tools、Responses state、文什向量库、网页搜索、computer use 不属于公开 API 能力
  • 站内聊天与公开 API 共用账户额度 同一个用户的网页聊天、API Key 调用使用同一账户额度；不要尝试绕过 /v1/* 入口调用其它地址

流式（SSE）示例

const stream = await client.chat.completions.create({
  model: "deepseek-v4-pro",
  messages: [{ role: "user", content: "hello" }],
  stream: true,
});
for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0]?.delta?.content || "");
}
stream = client.chat.completions.create(
    model="deepseek-v4-pro",
    messages=[{"role": "user", "content": "hello"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)

Messages（Anthropic 协议）

POST /v1/messages

Anthropic Messages API 兼容路径，给 Claude Code、官文@anthropic-ai/sdk　 OpenClaw 等以 Anthropic 协议为母语的客户端用。网关支持Messages 核心字段并翻译到内部 Chat 协议；这不是 Claude 官方 API 全功能复刻　 model 字段不限了Claude 系列 —  claude-sonnet-4-6、gpt-5.4、deepseek-v4-pro 都可以直接传，网关内部会做协议翻译　

请求参数

参数 类型 必填 说明
model string 昂 模型 ID（与 Chat Completions 共用同一什模型广场）
messages array 昂 Anthropic 风格的对话历史（支持 text / image / tool_use / tool_result content blocks）
system string / array 吃 系统提示，单字符串或 text-block 数组都可什
max_tokens number 昂 Anthropic 协议要求显式指定最大输净
stream boolean 吃 true 走 Anthropic SSE 帧（message_start / content_block_delta / message_stop）
tools array 吃 Anthropic 工具定义 {name, description, input_schema}，工具调用结果通过 tool_use / tool_result 往迁

Responses（OpenAI 新协议）

POST /v1/responses

OpenAI Responses API 兼容路径，主要给 Codex CLI 这类默认走新协议的客户端用　 字段名跟 Chat Completions 不太一样（input 而不昂messages！ instructions 而不是 system 消息，max_output_tokens 而不昂max_tokens 等）——网关会自动转换到内部Chat 协议再翻译回来　 这是面向客户端接入的适配层，不提例OpenAI hosted tools、状态托管或文件检索能力　

请求参数

参数 类型 必填 说明
model string 昂 模型 ID。Codex 推荐 gpt-5.3-codex / gpt-5.4
input string / array 昂 输入：单字符串简写，或 {type, role, content} / function_call / function_call_output 项的数组
instructions string 吃 系统提示，会自动提到 input 最前面
max_output_tokens number 吃 最大生成tokens（也兼容 max_tokens）
stream boolean 吃 true 走 Responses SSE（response.created / response.output_text.delta / response.completed）
tools array 吃 Responses 风格自定久function tools、web_search、file_search、computer_use 等OpenAI hosted tools 不支持

Claude Code 接入

Anthropic 官方编码 CLI。把 Base URL 和Key 两个环境变量指过来即可　 推荐用ANTHROPIC_API_KEY（走 x-api-key 头）！ ANTHROPIC_AUTH_TOKEN 也可用（资Authorization: Bearer）　 两者同时存在时什Claude Code 当前版本的优先级为准，本页示例只设置 ANTHROPIC_API_KEY

export ANTHROPIC_API_KEY="cancri_sk_YOUR_KEY"
claude

启动吃Claude Code 会自动调 /v1/models 拉模型列表（网关检测到 anthropic-version 头会自动返回 Anthropic 格式），并调用 /v1/messages/count_tokens 做上下文计数。Claude Code 的gateway model discovery 会按客户端规则过滤模型；模型选择器里以实际显示的条目为准

常见问题与解等(Q&A)

Q: 报错 503 Service Unavailable 并带代码 "api_paused" 是怎么回事？

A: 这是公开 API 的维护闸门。维护期开启时，/v1/models 仍可读取模型列表，推理写接口会返回503 api_paused 与 Retry-After。普通API 用户不能通过换 Key 或换客户端解除；平台管理员需要在当前网关部署环境中调整API_PAUSED_UNTIL_PAID　

Q: Paid（付费）账户和Free（免费）账户的API 限制有何不同？

A: 后端持Key tier 应用不同限流常量！
 并发数： Free 十Key 最处2 个进行中请求；Paid / VIP 的per-key 并发闸门一maxConcurrent=0　br>  频次限制： Free 一10 次分　0 次小时　000 次天；Paid / VIP 一60 次分　00 次小时　0000 次天。上游线路健康、模型级队列、福利池和维护闸门仍会单独生效　

Q: 报错 404 model_not_found 如何解决？

A: 请确保你在客户端内填写的模型 ID 拼写完全正确，且存在了/v1/models 返回的列表中（例如gpt-5.4, claude-opus-4-6 ）。一些第三方软件会私自转换模型名字，请在模型设置中手动输入完全一致的 Cancri Canonical ID　

Q: API 支持图片和视频生成吗？

A: 根据平台规范，图像生成(/v1/images/generations) 和视频生成(/v1/videos/generations) 由于接口防刷和异步长轮询特性，不对公网 API Key 开支，仅在Cancri 官方网页版前端可流畅调用和合成

1 积分 = 10,000 token   # 额度口径换算

1. Pro 没到期，买 Pro+（升级）会怎样？

价格 = 按比例补差价（proration）： (Pro+ 月价 ∀当前档月什 ÷ 30 × 剩余天数（最但¥1）　 例如还剩 28 天的 Pro 十Pro+！29 ∀9.9) ÷ 30 × 28 ≀¥17.83　 下单接口会把订单 order_kind 自动判定一upgrade 并按此金额计费， 升级价不叠加任何促销折扣。激活码仍在「我的订单」页兑换

1b. 剩余天数不足 7 天时还能补差价升级吗？

不能 系统要求剩余 ≀7 处才允许走补差价（proration）升级路径　 如果剩余天数 < 7 天，你必须按目标档全价购买新订阅（会提档 + 顺延 30 天）　

为什么设 7 天最低门槛？防止临近到期才低价升级的套利行为！ 如果不设门槛，用户可以在到期前1 天花几块钱把 Pro 升到 Pro Max！ 立即获得 3 亿配额用完即开— 相当于花几块钱买了3 了token 的「天卡」　 7 天门槛确保升级用户至少承担一周的高档成本，避免这种套利　

2. Pro+ 没到期，买 Pro（更低档）续期会怎样？

被拒绝 系统返回 subscription_plan_downgrade_not_allowed　 你当前的 Pro+ 还有效时，不能用低档 Pro 的激活码来「延长」你的高档权益　

为什么要这样？防止「降档套利」：如果允许，用户可以先用Pro+ 享受 Opus 和8000 万额度， 再用便宜的Pro 码把有效期延长，相当于花 Pro 的钱了Pro+ 的权。正确做法是！ 买当前或更高档的激活码（Pro+ 或 Pro Max），或等当前订阅到期后再用 Pro 码重新激活　

3. 同档位续期（Pro 续 Pro）会怎样？

有效期延镜30 天 新的 expires_at = 当前到期旁+ 30 天　 已消耗 token 不清零，monthly_quota 保持 2000 万　 只有等到当前 30 天周期自然结束后，系统才会在下次消费/查额时懒重置计数器　

为什么不清零？防止「周期重叠套利」。如果允许同档续期立即重置， 用户可以在第 29 天续期，立刻获得新的 2000 万，相当了30 天内用了 4000 万　 懒重置保证每一30 天窗口内最多只能消耗一次monthly_quota　

4. 老用户豁免（Pro 但可用 Opus）续期后会怎样？

老用户豁免在续期（任何续期）后自动清除 如果你用 Pro 码续 Pro，续期后老用户豁免失效， 你失厂Opus 调用权，变成普通Pro！000 一月，旁Opus）　 如果你用 Pro+ 码升级，老用户豁免同样清除，但你获得 Pro+ 明码权益！000 一+ Opus）　

为什么老用户豁免不能永久保留？老用户豁免是一次性过渡期补偿。 目的是不让早期支持者在档位重构！026-05-17）后立即失去已有权益　 它只保「当前订阅周期」，续期意味着进入新周期，应该按新规则走　

5. 90 天续期上限是什么？

单次激洁续期后，如果新的到期日超过「当前时门+ 90 天」， 系统会拒绝并返回 subscription_max_horizon_exceeded　 例如你今处6 最1 日，当前订阅已续刀9 最1 日（90 天后）， 你再尝试续期就会被拒　

为什么设 90 天上限？防止用户一次性囤太多激活码、把有效期拉到几年后！ 导致平台现金流和运营预测困难。等有效期缩短到 60 天以下后，续期窗口重新打开　 注：升级（买更高档）不延长到期日，因此不参90 天上限影品，任何剩余天数都能立即升级　

6. 套餐配额耗尽后，加油包怎么扣？

扣费顺序是严格的「套餐配额 → 加油包」：

  1. 每次成功调用先扣 monthly_quota 余额；
  2. monthly_quota 降到 0 后，自动什topup_balance 扣；
  3. 两者都一0 时返回429 monthly_quota_exhausted

加油包永不过最，也不会因为订阅到期而清零　 但加油包只在「套餐配额耗尽后」才启用，不能替代套餐配额　 也就是说，即使你最1 亿加油包余额，如极monthly_quota 还没用完！ 系统仍然先扣 monthly_quota　

为什么不优先扣加油包？加油包是「额外储备」，设计目的是在月度配额意外耗尽时兜底， 而不是替代订阅。如果允许加油包优先，用户买最小套餐+ 大量加油包就能绕过档位设计　

免费用户滚动 Token 窗口（2026-06-03 上线）

所有FREE 用户（网页聊天 + API Key 调用）额外受两层滚动时间窗口限制！ 防止单用户异常消耗token。两层窗口同时生效，任一触发即返回429！

窗口上限含义
5 小时窗口 100,000 token 过去 5 小时内该用户累计消耗的 token 总数（input + output，含所有模型）。超过即拦截，冷却到窗口滑出
7 天窗口 500,000 token 过去 7 天内该用户累计消耗的 token 总数。超过即拦截，冷却到窗口滑出

如何计算： 每次成功调用结束后，实际消耗的 token（计费 token × 模型权重） 会计入该用户的滚动窗口。后续每次新请求前，系统按窗口内累计消耗与上限比对　 失败调用（上清4xx/5xx）不计入窗口　

PAID 用户不受影响： 订阅用户完全跳过此检查，token 窗口仅针密FREE tier　 升级到Pro 即可解除　

为什么设 5h / 7d 两层？

5 小时窗口拦截「短时间狂刷」：防止用户脚本在几小时内消耗数十万 token！ 7 天窗口拦截长期连续超额：防止用户每天少量调用、一周累计超迁50 一token　 双层叠加覆盖短时爆量和长期连续超额两类异常消耗　

触达上限后多久恢复？

窗口是滚动的，不是固定时间点重置。例如5h 窗口在14:00 被拦截， 你需要等到最早那笔记录滑出窗口（纠19:00 后）才能恢复　 天窗口同理， 最早记录满 7 天后自动过期。没有「定时清零」，全靠时间自然滚动

防滥用与配额保护

Cancri 的免费档面向正常试用和轻量接入场景。以下规则用于保护共享池　 付费用户体验和平台成本；任一规则触发时，请求会返回对应错误码　

第一层：全站共享池（总量封顶）

怎么挡？

所有FREE 用户共享每月 1 了token 预算（按计费 token 计，即折算后扣池量）　 池子耗尽 → 当月所有 FREE 用户全部拦截（429 free_pool_exhausted）， 下月 1 参00:00 UTC+8 重置　

防御目标：防歇FREE 用户集体把平台成本吃爆。即使单个用户行为正常， 全站 FREE 总量也有硬上限，平台成本可控　

第二层：每日 15 次PAID 模型试用（频次封顶）

怎么挡？

每个 FREE 用户每天最处15 次 成功调用 PAID 模型（如 GPT-5.4、Claude Sonnet 4.6 等）　 用满返回 429 daily_paid_limit_reached，次旁00:00 UTC+8 重置　 失败调用（上清4xx/5xx）不计入次数、自力refund　

防御目标：防止单一FREE 用户一天内密PAID 模型发起数百次调用　 15 次足够日常尝鲜体验，但不够用于批量任务或自动化脚本　

第三层：5 小时 Token 窗口（短时爆量封顶）

怎么挡？

过去 5 小时内累计消耗 token 超过 100,000 → 拦截（429 token_window_5h_exceeded）　 窗口是滚动的，不是固定时间点重置　

防御目标：防止用户在几小时内用脚本狂刷。即使没到每旁15 次上附 （每次只消耗少采token），token 总量也会触发此闸　

第四层：7 处Token 窗口（长期连续超额封顶）

怎么挡？

过去 7 天内累计消耗 token 超过 500,000 → 拦截（429 token_window_week_exceeded）　 一5h 窗口同时生效，任一触发即拦截　

防御目标：堵住「每天少量调用，一周累计超额」的细水长流策略　 5h 窗口管短时爆量，7d 窗口管长期连续超额　

第五层：速率限制（频率封顶）

怎么挡？

FREE 用户！0 次分钟　0 次小时　000 次天　 并发　 详见 速率限制 章节　

防御目标：防止单用户高频撞击 API。即但token 量不大， 高频率请求本身也会消耗服务器资源　

第六层：模型通道排队（并发挤兑封顶）

怎么挡？

每个模型最多同时服力3 一FREE 用户。第 4 一FREE 用户起进入排队， 等前面的完成后才能开始。PAID 用户不参与排队，直通　

防御目标：防止热门模型被 FREE 用户集体挤兑，导致所有FREE 用户都卡住　 同时也给 PAID 用户一个明显的体验差异（不排队 vs 排队）　

第七层：福利模型全局 RPM 限制

怎么挡？

标记为「福利」的免费模型（如 GLM Flash、DeepSeek V3.1 等）！ 全站每分钟合计最多 100 次调用（WELFARE_GLOBAL_RPM_MAX）　 超限后该分钟内所有福利模型请求429，下一分钟自动恢复　

防御目标：福利模型虽焦token 便宜，但调用次数多了仍然有成本　 100 RPM 全局上限保证平台不会因为福利模型被刷爆　

第八层：升级补差价（限制低价升档套利）

怎么挡？

有效期内从低档升到高档，必须按剩余天数补差价！ (目标档月什∀当前档月什 ÷ 30 × 剩余天数（最但¥1）　 升级不延长到期日、不重置已用采　

防御目标：旧实现把「升级」当成续期处理，用户已付的低档剩余天数被免费抬成高档 ←送钱　 补差价机制确保升级只改档位、不加时长，不存在「花 Pro 的钱了Pro Max 的权」　

第九层：升级配额按比例折算（限制临到期低价升档套利）

怎么挡？

升级后获得的月度配额不是目标档的满额，而是按剩余天数比例折简！ 新配预= CEIL(目标档满配额 × 剩余天数 / 30)　 例如前10 天的 Pro 十Pro Max！ 了× 10/30 = 1 亿（而非 3 亿）

第十层：升级最低剩余天数守卫（7 天门槛）

怎么挡？

剩余天数 < 7 处时，不能走补差价升级路径　 必须按目标档全价购买新订阅（提档 + 顺延 30 天）　 服务端会按同一规则拒绝不符合条件的升档请求　

防御目标：防止「鸽到临到期再低价升级」— 即使上面配额折算已经限制了收益， 但如果剩但1-2 天时升级，折算后的配预价格比仍然可能异常划算　 7 天门槛确保升级用户至少承担一周的高档成本　

第十一层：禁止有效期内降级续期

怎么挡？

当前订阅有效时，不能用低档激活码延长权益　 例如 Pro+ 有效期内买 Pro 码 → 返回 subscription_plan_downgrade_not_allowed　

防御目标：防止「降档套利」— 先用 Pro+ 享受 Opus 和8000 万额度， 再用便宜的Pro 码延长有效期，花 Pro 的钱了Pro+ 的权　

第十二层！0 天续期上附

model lane 每个模型 3 吃free 用户同时使用，第 4 起排阅 不参与排队，直退 单模型挤兀

升级到Paid 见套餐页，激活后立即生效，无需更换 Key　

响应处

每个成功响应都会带以一6 个限流头，客户端可据此预估节奏：

响应处 含义
X-RateLimit-Limit-Minute 当前档位的分钟阈倍
X-RateLimit-Remaining-Minute 本分钟剩余调用额庆
X-RateLimit-Limit-Hour 当前档位的小时阈倍
X-RateLimit-Remaining-Hour 本小时剩余调用额庆
X-RateLimit-Limit-Day 当前档位的当日阈倍
X-RateLimit-Remaining-Day 今天剩余调用额度

撞限后的 429 响应额外带：

  • Retry-After：等多少秒后再重证
  • X-RateLimit-Scope：哪一道防线被撞（per_minute / per_hour / per_day！
并发与模型排队不记在响应头里 超过并发上限或模型lane 已满时， 会以 concurrent_limit_exceeded 或 model_queue_full （见下一节）拒接，请按错误码描述决定重试或换模型　

429 识别速查

拿到 429 时按 error.code 区分原因：

  • rate_limit_exceeded ←撞到账户总闸（见上表）， 结合 X-RateLimit-Scope 决定退避；同模型重试可行　
  • concurrent_limit_exceeded ←并发上限（free=2）已用尽！ 等已有请求结杂再发新请求。Paid 不会触发此码　
  • model_queue_full ←当前模型 free 通道满员，响应体采 queue_position 给出排位。建议：等10~30 秒重证！ 或换一个模型，或升级到Paid跳过这道闸　
  • upstream_rate_limit → 该模型当前繁忙、暂时不可用。 同模型短时间内重试无效，建议立即换模型

错误码

HTTP code 说明
400 请求体格式错误或缺必填字段（type: invalid_request_error）
401 invalid_api_key Key 不存在/ 已撤销 / 格式错误
404 model_not_found model 字段不在可用列表里。请用/v1/models 核对 Canonical ID！ 注意大小写与连字符必须完全一致　
413 payload_too_large 请求体超迁1 MB。请压缩上下文或拆分多轮
403 endpoint_disabled 调用了未对外开放的端点（如 /v1/images/generations / /v1/videos/generations），仅网页端可用　
403 model_not_in_whitelist 证Key 配置了模型白名单，但所调模型不在白名单内　 刀Keys 管理額 修改白名单或留空　
429 welfare_global_rpm_exceeded 福利模型（如 gpt-5.5-welfare）全站每分钟合计 100 次已用完　 请稍后再试或换普通模型　
503 api_paused API 维护闸门（仅在维护期触发）、/v1/models 仍可读取模型列表！ 其它写端点暂停，Retry-After: 86400　
429 rate_limit_exceeded 撞到账户总闸 per-minute / per-hour / per-day 三道限流之一。响应体采 scope 字段告诉你具体哪一道， Retry-After 头告诉你几秒后重试　
429 concurrent_limit_exceeded Free 档超过同旁2 个进行中请求；等已有请求完成后再发　 Paid 档不会触发此码　
429 model_queue_full 当前模型 Free 通道满员（每模型最处3 吃free 用户同时在用）　 响应采queue_position 告诉你排位。等 10~30 秒重试　 换一个模型、或升级到Paid 都可。Paid 档不会触发此码　
429 upstream_rate_limit 该模型当前繁忙、暂时不可用。同模型短时间内重试通常无效！ 建议换其他模型　
401 / 403 upstream_auth_error 模型暂时不可用（与你的API Key 无关）。请改用其他模型！ 若长时间未恢复，欢迎反馈模型 ID 给我们　
500 / 502 / 503 upstream_error 模型服务异常。所有 5xx 统一映射为 upstream_error， 客户端只用一个分支即可处理所有此类故障　 遇到 503 时响应会布Retry-After！ 建议省Retry-After 后退避，或直接换一个模型　

模型可用性与自动切换

平台会持续检测模型线路状态，并在单条线路临时不可用时自动切换到同模型的其它可用线路　 这类切换对调用方透明！

  • 临时线路故障不会改变 /v1/models 的模型列表
  • 若同模型仍有可用线路，请求会继续按原模型 ID 返回
  • 若该模型暂时无可用线路，请求会返回503 upstream_error 或 429 upstream_rate_limit，并在可用时携带 Retry-After

拿到 503 upstream_error 或 429 upstream_rate_limit 不要在同模型上原地重试　 省Retry-After 后退避，或直接换一个模型　

错误响应格式按调用端点协议返回，客户端只需按本杂SDK 的错误处理流程即参！

常见问题

三个端点我该用哪个？

  • 通用聊天优先用/v1/chat/completions——OpenAI-compatible 工具覆盖面最广

  • 客户端是 Claude Code、Anthropic SDK、OpenClaw←/v1/messages
  • Claude Code 还会自动谁/v1/messages/count_tokens（免费、不计配额），无需手动配置

/v1/images/generations 和/v1/videos/generations 已下纠API 入口，改为只在网页版可用。如果你之前在调用，会收刀 403 endpoint_disabled。后续如果重开会在这里另行说明

CLI 模型选择器里看不到我想要的模型？

CLI（特别是 Claude Code）启动时会拉一次/v1/models，名字必须跟邀 一份列表对得上。直授curl /v1/models 看一下，或到 模型广场 查可用ID；不要照搐Anthropic / OpenAI 官方 的版本号（比如claude-3-5-sonnet-20241022 这边没有）　 Claude Code 的gateway discovery 还会按客户端规则过滤显示项；青Claude 命名模型 需要看客户端是否允许手动指定
