Cancri API 文档

OpenAI / Anthropic 双协议兼容的多模型聚合 API。一个 Key，OpenAI SDK、 Anthropic SDK、Codex CLI、Claude Code、OpenCode、OpenClaw 都能直接接入。

概述

Cancri API 是一个统一接口层，把多个模型供应商（魔塔 / 百炼 / Claude / Gemini / OpenAI 兼容线路 等）封装在一个端点后面。同一把 Key，三种协议 ——选你的客户端原生支持的那一种就行：

路径 协议 适合的客户端
POST /v1/chat/completions OpenAI Chat Completions openai SDK、LangChain、LiteLLM、OpenCode 等
POST /v1/responses OpenAI Responses Codex CLI（默认协议）
POST /v1/messages Anthropic Messages Claude Code、@anthropic-ai/sdk、OpenClaw
GET /v1/models OpenAI / Anthropic 自适应 带 anthropic-version header 时返回 Anthropic 格式
Base URL： https://diusqgphvybnzazgopor.supabase.co/functions/v1/api-gateway
  • 认证：Authorization: Bearer cancri_sk_xxx 或 x-api-key: cancri_sk_xxx
  • 支持流式（SSE）和非流式两种模式
  • 所有模型在 模型广场 可见
  • 图像 / 视频生成只在网页版开放，不对外 API 暴露
多线路冗余对你透明。 你看到的 model 字段（如 gpt-5.4、deepseek-v3）是统一的品牌 ID，后端会在 多条上游线路里按健康度自动选最优路由。某条线路抽风时其他线路自动接管， 你不需要改 model 字段。

认证

所有 API 请求都必须在 Authorization 头里带 Bearer Token。Key 形如：

cancri_sk_48 个十六进制字符

前缀 cancri_sk_（10 字符）+ 24 字节随机熵的十六进制（48 字符）= 总长度恒为 58 字符。 做 Key 长度校验的客户端按这个写。

  1. 到 申请页 提交申请
  2. 审核通过后到 Keys 管理页 生成 Key
  3. 把 Key 安全存好（生成后只显示一次）
⚠️ 不要在浏览器代码或开源仓库里硬编码 Key。 Key 一旦泄露， 立刻到 Keys 管理页撤销并重新生成。

每个账号最多同时持有 5 个 活跃 Key，超过需先撤销旧的。

Chat Completions

POST /v1/chat/completions

调用任意聊天模型生成回答，支持流式与非流式。

请求参数

参数 类型 必填 说明
model string 是 模型 ID，例如 deepseek-v4-pro。完整列表见 模型广场
messages array 是 消息历史，元素 {role, content}
stream boolean 否 设 true 启用 SSE 流式输出，默认 false
temperature number 否 0-2，越高越随机，默认 1
max_tokens number 否 最大生成 tokens，受模型能力上限约束
top_p number 否 0-1 核采样阈值
tools array 否 函数调用工具集（部分模型支持）

流式（SSE）示例

curl https://diusqgphvybnzazgopor.supabase.co/functions/v1/api-gateway/v1/chat/completions \
  -H "Authorization: Bearer cancri_sk_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -N \
  -d '{
    "model": "deepseek-v4-pro",
    "messages": [{"role":"user","content":"hello"}],
    "stream": true
  }'
const stream = await client.chat.completions.create({
  model: "deepseek-v4-pro",
  messages: [{ role: "user", content: "hello" }],
  stream: true,
});
for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0]?.delta?.content || "");
}
stream = client.chat.completions.create(
    model="deepseek-v4-pro",
    messages=[{"role": "user", "content": "hello"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)
SSE 格式： 每个事件以 data: 开头的 JSON 行， 最后以 data: [DONE] 结束。每个 chunk 的 choices[0].delta.content 是增量文本。

Messages（Anthropic 协议）

POST /v1/messages

Anthropic Messages API 兼容，给 Claude Code、官方 @anthropic-ai/sdk、 OpenClaw 等以 Anthropic 协议为母语的客户端用。请求体和响应体跟 Anthropic 一模一样， 但模型 ID 用我们这边的（claude-sonnet-4-6、gpt-5.4、 deepseek-v4-pro 等都行——网关会自动识别协议并代为翻译）。

请求参数

参数 类型 必填 说明
model string 是 模型 ID（与 Chat Completions 共用同一份 模型广场）
messages array 是 Anthropic 风格的对话历史（支持 text / image / tool_use / tool_result content blocks）
system string / array 否 系统提示，单字符串或 text-block 数组都可以
max_tokens number 是 Anthropic 协议要求显式指定最大输出
stream boolean 否 true 走 Anthropic SSE 帧（message_start / content_block_delta / message_stop）
tools array 否 Anthropic 工具定义 {name, description, input_schema}，工具调用结果通过 tool_use / tool_result 往返

非流式示例

curl https://diusqgphvybnzazgopor.supabase.co/functions/v1/api-gateway/v1/messages \
  -H "x-api-key: cancri_sk_YOUR_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \

    "model": "claude-sonnet-4-6",
    "max_tokens": 256,
    "system": "你是简洁的助手",
    "messages": [{"role":"user","content":"用一句话解释 RLS"}]
  }'

流式（SSE） 在请求里加 "stream": true 即可，输出严格符合 Anthropic 事件协议——message_start → content_block_start → content_block_delta×N → content_block_stop → message_delta → message_stop。Claude Code 默认走这条路径。

Responses（OpenAI 新协议）

POST /v1/responses

OpenAI Responses API 兼容，主要给 Codex CLI 这类默认走新协议的客户端用。 字段名跟 Chat Completions 不太一样（input 而不是 messages， instructions 而不是 system 消息，max_output_tokens 而不是 max_tokens 等）——网关会自动转换到内部 Chat 协议再翻译回来。

请求参数

参数 类型 必填 说明
model string 是 模型 ID。Codex 推荐 gpt-5.3-codex / gpt-5.4
input string / array 是 输入：单字符串简写，或 {type, role, content} / function_call / function_call_output 项的数组
instructions string 否 系统提示，会自动提到 input 最前面
max_output_tokens number 否 最大生成 tokens（也兼容 max_tokens）
stream boolean 否 true 走 Responses SSE（response.created / response.output_text.delta / response.completed）
tools array 否 Responses 风格 {type:"function", name, description, parameters}。web_search/file_search 等内置工具暂不支持

速率限制

每个 Key 同时受 4 道防线 保护，任何一道撞上都会返回 429 + Retry-After。不分模型档位，所有 Key 使用同一套阈值：

防线 阈值 拦什么
per-minute 10 次 / 分钟 脚本狂推、瞬间爆量
per-hour 60 次 / 小时 持续高频撞击
per-day 1000 次 / 天 24h 挂机慢刷
concurrent 2 个同时进行 多线程并发刷

响应头

每个成功响应都会带以下 6 个限流头，客户端可据此预报手节奏：

响应头 含义
X-RateLimit-Limit-Minute 当前分钟阈值（10）
X-RateLimit-Remaining-Minute 本分钟剩余调用额度
X-RateLimit-Limit-Hour 当前小时阈值（60）
X-RateLimit-Remaining-Hour 本小时剩余调用额度
X-RateLimit-Limit-Day 当日阈值（1000）
X-RateLimit-Remaining-Day 今天剩余调用额度

撞限后的 429 响应额外带：

  • Retry-After：等多少秒后再重试
  • X-RateLimit-Scope：哪一道防线被撞（per_minute / per_hour / per_day）
并发限制不记在响应头里。超过 2 个同时请求时，额外请求会被 concurrent_limit_exceeded（如下一节）拒接，请等其他请求返回后重试。

per-model 上游限制（重要）

上面 4 道防线是 gateway 层的总闸，控制整个 API Key 的总调用量。 每个模型还会受到其上游线路自身的速率限制，这部分不在我们 gateway 的控制范围内，且各家阈值不同（部分免费线路可能低至 10 次/小时）。

当上游 per-model 限速被撞，会返回：

  • HTTP 429
  • error.code = "upstream_rate_limit"
  • error.type = "rate_limit_error"
  • error.message 里会以 "upstream details" 附上上游原始信息（仅供排查；具体文本随上游变化，不要用作判定依据）
识别规则：拿到 429 时 error.code 必看：
  • rate_limit_exceeded → 撞到 gateway 总闸（见上表）， 结合 X-RateLimit-Scope 决定退避；同模型重试可行。
  • upstream_rate_limit → 该模型的上游线路被限速， 同模型短时间内重试无效，建议立即换模型。
  • concurrent_limit_exceeded → 等已有请求结束。

错误码

HTTP code 说明
400 — 请求体格式错误或缺必填字段（type: invalid_request_error）
401 invalid_api_key Key 不存在 / 已撤销 / 格式错误
404 model_not_found model 字段不在可用列表里。两种可能：不存在或 被健康度临时隐藏（见下节）。
413 payload_too_large 请求体超过 1 MB。请压缩上下文或拆分多轮。
429 rate_limit_exceeded 撞到 gateway 总闸 per-minute / per-hour / per-day 三道限流之一。响应体里 scope 字段告诉你具体哪一道， Retry-After 头告诉你几秒后重试。
429 upstream_rate_limit 该模型的上游线路被限速（不是 gateway 层）。 通常重试同模型短时间内无效，建议改用其他模型。 error.message 末尾会带上游原始信息以便排查。
429 concurrent_limit_exceeded 超过同时 2 个进行中请求。等剩余请求完成后再发。
401 / 403 upstream_auth_error 该模型的上游凭证被拒（不是你的 API Key 问题）。请改用其他模型， 并向我们反馈受影响的模型 ID。
500 / 502 / 503 upstream_error 上游模型供应商出错或返回非法 JSON。所有 5xx 都统一映射成 upstream_error，不会出现 service_unavailable 等其它 code——这是为了让客户端只用一个分支处理 所有上游故障。503 还会带 Retry-After，表示该模型被临时 熔断（一小时滑动窗口内连续失败）；改用其他模型即可，无需等待。

模型健康度自动隐藏

为了不让你在坏掉的上游上浪费重试额度，后端会以 1 小时为滑动窗口记录每个 模型的调用成功率：

  • 调用 ≥ 3 次 且 成功率 < 30% → 临时从模型列表隐藏（返回 404 model_not_found）
  • 一小时后如果指标恢复→ 自动重新出现在列表里，无需人工介入
  • 如果反复故障→ 继续按滑动窗口隐藏

如果你之前能调通的模型突然 404，请出 模型广场 确认它是否还在列表里。不在→ 等1 小时后重试。

所有错误响应都符合 OpenAI 的错误格式：

{
  "error": {
    "message": "...",
    "type": "invalid_api_key",
    "code": "invalid_api_key"
  }
}

常见问题

三个端点我该用哪个？

  • 无脑用 /v1/chat/completions——支持的 SDK / 工具最多，调用最稳。
  • 客户端是 Codex CLI、想走它的默认协议→ /v1/responses。
  • 客户端是 Claude Code、Anthropic SDK、OpenClaw→ /v1/messages。

图像生成怎么没了？

/v1/images/generations 和 /v1/videos/generations 已下线 API 入口，改为只在网页版可用。如果你之前在调用，会收到 403 endpoint_disabled。后续如果重开会在这里另行说明。

CLI 模型选择器里看不到我想要的模型？

CLI（特别是 Claude Code）启动时会拉一次 /v1/models，名字必须跟那 一份列表对得上。直接 curl /v1/models 看一下，或到 模型广场 查可用 ID；不要照搬 Anthropic / OpenAI 官方 的版本号（比如 claude-3-5-sonnet-20241022 这边没有）。

tool calling（function calling）支持吗？

三条路径都支持，自定义 function 工具会原样翻译往返。但 Responses 协议 的 web_search / file_search / computer_use 等内置工具暂未实现，传过来会被忽略。

怎么追踪用量？

到 Keys 管理页 可看到每个 Key 的最后使用时间和调用统计。详细的 token 消耗后续会上线。

能在浏览器里直接调吗？

不要。Key 暴露在前端等于免费送给所有人。请始终从你的服务端转发。

支持的国家/IP 限制？

后端会做地域级速率限制和 IP 维度风控，但不主动屏蔽国家。 如发现可疑流量会临时封锁。

Key 丢了怎么办？

生成时只显示一次，无法找回。到 Keys 管理页 撤销旧 Key，重新生成。

能在 TRAE IDE 里用吗？

暂时不行。 字节跳动的 TRAE IDE 目前在「自定义模型」里只允许填 Model ID 和 API Key 两个字段，不开放 Base URL 设置，所以 TRAE 的请求只能 发到官方 api.openai.com，没办法指过来 Cancri。这是 TRAE 自身的能力 缺失，跟踪官方 issue #1206 / #963。 等 TRAE 加上 base_url 字段后，配置方法跟 OpenCode 完全一致。

急用的话可以参考开源项目 arch3rPro/Trae-Proxy， 它通过本地 hosts 重定向 + 自签证书把 OpenAI 域名劫持到自定义后端。需要管理员权限， 折腾门槛较高，不推荐普通用户。

计费怎么算？

目前所有 Key 都是 free tier，按速率限制控制成本，不 按 token 计费。商业化定价后会提前通知。
