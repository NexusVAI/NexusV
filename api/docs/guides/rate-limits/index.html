速率限制

速率限制按账户计算，只有 RPM 和 TPM 两项，档位由累计充值或套餐决定。

速率限制按账户生效：同一账户的网页、桌面端、Bot 与 API 调用共用一组限额，增加密钥不会提高限额。团队密钥使用团队自己的限额，见团队。

限额只有两项：

  • RPM：每分钟请求数。
  • TPM：每分钟 token 数，输入与输出合计。

不限制同时进行的请求数，也没有按小时或按天计的请求数与 token 上限。免费模型的总用量另受免费额度限制。

档位由累计充值决定：

Tier 0¥0602,000,000
Tier 1≥ ¥101202,000,000

Tier 4≥ ¥3005,0004,000,000
Tier 5≥ ¥1,00010,0005,000,000
  • 有效套餐有对应的保底档位：Go 为 Tier 1，Plus 为 Tier 2，Pro 为 Tier 3。套餐档位与累计充值档位取较高者。
  • 代金券与赠送额度不计入累计充值。
  • 档位提升通常在 1 分钟内生效，无需更换密钥。
  • 团队按累计划转到团队余额的金额定档，不继承成员的套餐或充值。

充值见控制台的账单页。

计量方式

RPM 和 TPM 都是令牌桶：容量等于每分钟的限额，按时间连续回填，而不是在整分钟清零。所以短时间内最多可以用满一分钟的额度，之后按回填速度继续。

  • 开始时预占。每个请求开始时消耗 1 个 RPM，并按「预估输入 token + 输出上限」预占 TPM。输出上限就是 max_tokens（Responses 为 max_output_tokens）；没设置时按该模型的最大输出 token 数预占。
  • 结束后多退少补。响应结束后按实际用量结算 TPM，多占的部分退回。
  • 允许短暂超出。只要账户还有剩余 TPM，请求就会被接受，所以单次大请求可以让余量暂时变成负数，之后由回填补足。
  • 单次请求过大。单次请求的预占量超过本档 TPM 的 4 倍时，返回 429 request_too_large。
  • 失败的请求也计入 RPM。已经通过限速检查的请求，即使后来失败，也消耗 RPM。

给 max_tokens 设一个贴近实际需要的值，能减少 TPM 预占，让同一档位承载更多并发请求。实际扣费只按真实用量计算。

密钥级 RPM

如果密钥设置了 RPM 上限，它只能比账户限额更严：实际生效的是两者中较小的一个。超出密钥级上限时返回 429 rate_limit_exceeded，error.scope 为 key。

响应头

OpenAI 协议端点（/v1/chat/completions、/v1/responses）返回以下响应头：

响应头说明
x-ratelimit-limit-requestsRPM 上限
x-ratelimit-remaining-requests剩余的请求数
x-ratelimit-reset-requests请求额度恢复到上限所需的时间
x-ratelimit-limit-tokensTPM 上限
x-ratelimit-remaining-tokens剩余的 token 数
x-ratelimit-reset-tokenstoken 额度恢复到上限所需的时间

reset 的值是时长，如 1s、6m0s。

Anthropic 协议端点（/v1/messages）返回 anthropic-ratelimit-requests-limit、anthropic-ratelimit-requests-remaining、anthropic-ratelimit-requests-reset，以及对应的 anthropic-ratelimit-tokens-limit、anthropic-ratelimit-tokens-remaining、anthropic-ratelimit-tokens-reset。reset 的值是 RFC 3339 时间；剩余 token 数向下取整到千位。

请求数相关的响应头取当前最严的一层（账户或密钥）。
