20import com.openai.client.OpenAIClient;
import com.openai.client.okhttp.OpenAIOkHttpClient;
import com.openai.models.responses.Response;
import com.openai.models.responses.ResponseCreateParams;

public class Main {
  public static void main(String[] args) {
    OpenAIClient client = OpenAIOkHttpClient.fromEnv();

    ResponseCreateParams params =
        ResponseCreateParams.builder().input("Say this is a test").model("gpt-6-astra").build();

    Response response = client.responses().create(params);
    response.output().stream()
        .flatMap(item -> item.message().stream())
        .flatMap(message -> message.content().stream())
        .flatMap(content -> content.outputText().stream())
        .forEach(outputText -> System.out.println(outputText.text()));
  }
}

1234567891011121314[

    "id": "msg_67b73f697ba4819183a15cc17d011509",

    "role": "assistant",
    "content": [
      {
        "type": "output_text",

        "annotations": []
      }
    ]

output 数组中往往不止一项！它可能包含工具调用、推理模型生成的推理 token 数据以及其他项。不要假定模型的文本输出一定位于 output[0].content[0].text。

为方便使用，我们的一些官方 SDK在模型响应上提供了 output_text 属性，它会把模型的全部文本输出合并为一个字符串。如果只想快速取得文本输出，这个属性很有用。

选择模型

通过 API 生成内容时，首先要选择模型，也就是上面代码示例中的 model 参数。完整的可用模型列表见此处。选择文本生成模型时可以考虑以下几个因素。

  • 推理模型会先在内部生成思维链来分析输入提示，擅长理解复杂任务和多步骤规划。通常，它们比 GPT 模型更慢，成本也更高。
  • GPT 模型速度快、性价比高、智能程度也很高，但需要更明确的指令来说明如何完成任务。
  • 大模型与小模型（mini 或 nano）在速度、成本和智能程度之间各有取舍。大模型更擅长理解提示并跨领域解决问题，小模型通常更快、更便宜。

拿不准时，可以先用 gpt-6-astra，它是通用文本生成和提示词迭代的可靠默认选择。

提示词工程

提示词工程是为模型编写有效指令的过程，目的是让模型稳定地生成符合你要求的内容。

模型的输出具有不确定性，因此要得到理想结果，提示词既是艺术也是科学。不过，只要运用合适的技巧和最佳实践，就能稳定地获得好结果。

有些提示词技巧对所有模型都适用，例如合理使用消息角色。但不同类型的模型（如推理模型和 GPT 模型）可能需要不同的提示方式才能获得最佳结果，即使是同一系列的不同快照，结果也可能不同。因此，在构建更复杂的应用时，我们强烈建议：

  • 将生产应用固定到特定的模型快照（例如 gpt-4.1-2025-04-14），以保证行为一致
  • 编写测试和评估套件来衡量提示词的行为，以便在迭代提示词、或更换和升级模型版本时持续监控效果

接下来，我们看一看构造提示词时可用的工具和技巧。

消息角色与指令遵循

你可以结合 instructions API 参数与消息角色，向模型提供具有不同权威层级的指令。

instructions 参数向模型提供生成回复时的高层指令，包括语气、目标以及正确回答的示例。通过这种方式提供的指令优先于 input 参数中的提示。

OpenAI 模型规范描述了模型如何为不同角色的消息赋予不同的优先级。

developer user assistant
developer 消息是应用开发者提供的指令，优先级高于 user 消息。 user 消息是终端用户提供的指令，优先级低于 developer 消息。 模型生成的消息使用 assistant 角色。

多轮对话可以由这些类型的多条消息组成，并包含你和模型提供的其他内容类型。进一步了解如何管理对话状态。

可以把 developer 消息和 user 消息类比为编程语言中的函数及其参数。

  • developer 消息提供系统的规则和业务逻辑，相当于函数定义。
  • user 消息提供输入和配置，developer 消息中的指令会作用于这些内容，相当于函数的参数。

在代码中管理提示词版本

把生产环境的提示词存放在应用代码中，而不是创建可复用的提示词对象。由代码管理的提示词可以使用有类型的输入、代码评审、测试以及常规的部署流程来改变模型行为。

OpenAI 正在弃用 API 中可复用的提示词对象。自 2026 年 6 月 3 日起，不再推荐创建提示词，v1/prompts 计划于 2026 年 11 月 30 日下线。当前时间线请参阅弃用说明页。

对于新的文本生成工作：

  • 把提示词构建函数放在它所服务的功能附近的小模块中。
  • 对客户数据、文件或任务选项等动态值，使用有类型的函数参数或 schema。
  • 把生成的 instructions 和 input 直接传给 Responses API。
  • 修改生产提示词之前，先添加有代表性的样例、测试和评估检查。
  • 通过你的部署系统发布提示词修改；需要分阶段发布时，使用功能开关或配置。

如果你的集成通过提示词 ID 或版本调用已保存的提示词，请参阅提示词对象迁移指南，把该提示词迁移到代码中。

使用 Markdown 与 XML 设置消息格式

编写 developer 和 user 消息时，可以结合使用 Markdown 格式和 XML 标签，帮助模型理解提示词和上下文数据的逻辑边界。

Markdown 标题和列表有助于划分提示词的不同部分，并向模型传达层级关系。在开发过程中，它们还能让提示词更易读。XML 标签可以划定某段内容（例如用作参考的资料）的起止位置。XML 属性还可以为提示词中的内容定义元数据，供你的指令引用。

一般来说，developer 消息包含以下几部分，通常按此顺序排列（具体的最佳内容和顺序可能因所用模型而异）：

  • 身份：说明助手的用途、沟通风格和总体目标。
  • 指令：提供模型完成工作时的高层指引，包括应遵循的规则，以及应做什么、绝不应做什么。根据你的场景，这一部分可以细分为多个小节，例如模型如何调用自定义函数。
  • 示例：给出可能的输入示例，以及模型应给出的期望输出。
  • 上下文：提供模型生成回复可能需要的任何额外信息，例如训练数据之外的私有或专有数据，或你知道特别相关的其他数据。这部分内容通常最好放在提示词末尾附近，因为不同的生成请求可能需要不同的上下文。

通过提示词缓存降低成本与延迟

构造消息时，应把你会在 API 请求中反复使用的内容放在提示词开头，并且放在传给 Chat Completions 或 Responses 的 JSON 请求体中靠前的参数位置。这样可以最大化提示词缓存带来的成本和延迟节省。

少样本学习

少样本学习通过在提示词中加入几组输入与输出示例，引导大语言模型完成新任务，而不必对模型进行微调。模型会从这些示例中隐式地“领会”规律，并应用到新的提示上。提供示例时，应尽量覆盖多种可能的输入以及对应的期望输出。

通常，你会把示例放在 API 请求的 developer 消息中。下面的 developer 消息示例通过几组样例，告诉模型如何区分正面和负面的客户服务评价。

加入相关的上下文信息

在提示词中加入模型可用于生成回复的额外上下文信息，通常很有用。常见原因有以下几种：

  • 让模型能够访问专有数据，或训练数据集之外的其他数据。
  • 把模型的回复限定在你认为最有价值的一组特定资源之内。

这种在模型生成请求中加入额外相关上下文的做法，有时被称为检索增强生成（RAG）。你可以通过很多方式向提示词添加上下文，例如查询向量数据库并把返回的文本放进提示词，或者使用 OpenAI 内置的文件搜索工具，根据上传的文档生成内容。

规划上下文窗口

模型在一次生成请求中能够处理的上下文数据量有限。这一限制称为上下文窗口，以 token 计量（即你传入的数据块，可以是文本，也可以是图像）。

不同模型的上下文窗口大小不同，较新的 GPT-4.1 模型从十万级到一百万 token 不等。各模型的具体上下文窗口大小请参阅模型文档。

当前模型的提示方式

像 gpt-6-astra 这样的 GPT 模型，适合接收精确的指令，即在提示词中明确给出完成任务所需的逻辑和数据。要充分发挥最新模型的能力，请先阅读当前的提示指南。

编程

让 gpt-6-astra 处理编程任务时，遵循以下几条最佳实践效果最好：定义智能体的角色，用示例约束结构化的工具调用，要求充分测试以保证正确性，并设定 Markdown 规范以保持输出整洁。

大型代码库中的集成

在较大的代码库中做前端工作时，我们发现，在提示词中加入以下几类指令效果最好：

  • 原则：设定视觉质量标准，使用模块化、可复用的组件，并保持设计一致。
  • UI/UX：说明字体排版、颜色、间距与布局、交互状态（悬停、空状态、加载中）以及无障碍要求。
  • 结构：定义文件和文件夹布局，以便无缝集成。
  • 组件：给出可复用的封装示例，以及前后端调用的分离策略。
  • 页面：为常见布局提供模板。
  • 智能体指令：要求模型确认设计假设、搭建项目脚手架、执行规范、集成 API、测试各种状态并为代码编写文档。

智能体任务

对于使用 gpt-6-astra 的智能体及长时间运行的任务，提示词应聚焦三项核心实践：充分规划任务以确保彻底完成，在做出重要的工具调用决策时给出清晰的前言说明，并使用 TODO 工具有条理地跟踪工作流程和进度。

规划与坚持 指示模型在交还控制权之前彻底解决完整的问题，把问题拆解为子任务，并在每次工具调用后回顾结果以确认完整性。

推理模型的提示方式

与提示 GPT 模型相比，提示推理模型时有一些不同之处需要注意。一般来说，对于只给出高层指导的任务，推理模型通常能给出更好的结果。这与 GPT 模型不同，后者更依赖非常精确的指令。

可以这样理解推理模型和 GPT 模型的区别：

  • 推理模型就像一位资深同事。你可以给它一个要达成的目标，并相信它能自行摸清细节。
  • GPT 模型就像一位初级同事。给它明确的指令，让它生成特定输出时，效果最好。
