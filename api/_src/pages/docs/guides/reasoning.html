推理模型适合多步骤问题，例如复杂代码分析、规划和比较候选方案。用 NexusVAI API 试用时，先在模型目录确认能力与上下文长度，再用代表性问题比较质量、延迟和费用。

开始使用推理

通过 Responses API 发送任务说明。先按照快速开始设置 CANCRI_API_KEY，并确认示例模型 ID 在 GET /v1/models 中可用。

curl https://cn.nexusvai.xyz/v1/responses \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $CANCRI_API_KEY" \
  -d '{"model":"gpt-6-astra","reasoning":{"effort":"high"},"input":"比较三种数据备份方案，并说明各自如何验证可恢复。"}'

推理强度

Responses 使用 reasoning.effort；Chat Completions 使用 reasoning_effort。这些字段只对支持它的模型生效。各协议的取值和限制见 Responses 指南与 Chat Completions 指南。

选择推理模式

从模型默认行为开始，只有代表性测试显示质量收益时才提高强度。遇到需快速回答的请求，可用较低强度或更快的模型；不要假定其他平台的模式和取值与本站相同。

推理的工作原理

模型可能先消耗一部分输出预算完成内部推理，再给出可见答案。不要依赖内部推理文本：应用应以最终答案、可验证的结论和工具结果为准。

控制成本

让输入涵盖必要的规则、约束和相关数据，去掉无关上下文。用 max_output_tokens 限制 Responses 的输出预算，并给复杂任务留出空间；用量和费用在用量记录与价格页核对。

跨调用管理上下文

网关不保存服务端会话。把对话历史以及需要保留的函数调用和函数结果放进下一轮 input；不要用 previous_response_id 代替历史。见多轮对话和函数调用往返。

在对话中调整推理强度

下一次请求可以在带上历史的同时选择新的 reasoning.effort。不要依赖未在 API 参考中列出的会话更新字段。

推理摘要

模型返回公开的推理文本时，Responses 响应可在 reasoning 输出项中提供摘要；该输出项不一定存在。正文仍从消息中的 output_text 读取。

提示词编写建议

明确目标、已知条件和成功标准；要得到验证材料时，要求列出假设、测试结果或依据，而不是要求展示内部思考。

应用场景示例

  • 为大型变更做规划：要求分步列出依赖、风险和每一步的验证方式。
  • 分析复杂数据：要求标明数据缺口，并解释结论依据。
  • 阅读代码：让模型指出可观察的错误和最小回归测试，而不是只给猜测。

更多例子见推理最佳实践。

推理模型在生成回复前会先使用内部的推理 token。这有助于模型制定计划、有效使用工具、比较不同方案、处理模糊之处，并解决更难的多步骤任务。推理模型尤其适合复杂问题求解、编程、科学推理和多步骤的智能体工作流。它们也是 Codex CLI（我们的轻量级编程智能体）的最佳模型。

大多数推理任务建议从 gpt-6-astra 开始。如需更低成本，可以考虑 gpt-5.6-terra；如需最低成本和延迟，可以选择 gpt-5.6-luna。如果你使用 GPT-5.6 或 GPT-6 模型，请参阅推理模式了解其 pro 选项。

推理模型配合 Responses API 效果更好。Chat Completions API 仍受支持，但使用 Responses 可以获得更好的模型智能与性能。

推理强度

reasoning.effort 参数用于调节模型执行任务时的推理强度。

支持的取值因模型而异，可能包括 none、minimal、low、medium、high、xhigh 和 max。较低的强度偏向速度和更少的 token 用量，较高的强度让模型思考得更充分，以提高回复质量。无论选择哪一档，模型都会根据任务难度调整推理：简单任务使用较少的 token，复杂任务则思考得更深入。

GPT-6 Astra 的推理强度不支持 none。将 reasoning.effort（Responses）或 reasoning_effort（Chat Completions）设为 none 会返回 HTTP 400。GPT-6.1 Sol 不支持 none 或 minimal，默认使用 medium。

请使用 Responses API 进行函数调用。Chat Completions 不支持以 GPT-6 Astra 或 GPT-6.1 Sol 进行函数调用。

默认值也因模型而异。gpt-5.5 默认使用 medium。要兼顾这个模型的质量、可靠性和性能，最好从这一档开始。

推理强度 适用场景
none 适合对延迟要求极高，且不需要推理或多次串联工具调用的任务。在对延迟敏感的场景中使用 gpt-5.5 时，建议先试用 low，必要时再改用 none。

常见场景包括语音、快速信息检索和分类。
low 延迟略有增加，仍能高效推理。适合需要使用工具、规划、搜索或多步决策，同时又要兼顾速度和成本的场景。

常见场景包括数据分析、起草文稿、以执行为主的编程，以及客服或聊天助手工作流。
medium 适合重视质量和可靠性，且涉及规划、复杂推理和判断的任务。这是大多数任务的默认配置，在延迟、性能和成本之间较为均衡。

常见场景包括智能体编程、研究、处理电子表格和幻灯片，以及委派长期任务。
high 适合高难度推理、复杂调试、深入规划，以及比起延迟更看重质量和模型能力的高价值任务。推荐用于复杂工作流和智能体任务。

常见场景包括智能体编程、长期研究和知识工作。可根据任务复杂程度，评估 medium 和 high 两档。
xhigh 适合深入研究、异步工作流和需要长时间运行的智能体任务。只有评估显示收益值得额外的延迟和成本时，才使用这一档。

常见场景包括安全审查、代码审查、提升企业工作效率、深入研究以及高难度的编程工作流。
max 为最复杂的任务提供最高推理强度。如果目前使用 xhigh，可以评估 max 是否能带来更好的表现。

在对延迟敏感的应用中，可以让模型先给出简短的开场说明，再深入推理，以缩短首个可见 token 的等待时间。

有些模型只支持上述取值中的一部分。选择前请查阅相应的模型页面。

推理模式

GPT-5.6 和 GPT-6 模型在 Responses API 中支持 standard 和 pro 两种推理模式，默认使用 standard。如果任务较难，需要模型进行更多计算，并能接受更高的延迟和 token 用量，可以将 reasoning.mode 设为 pro。

推理模式与推理强度相互独立。模式决定用 standard 还是 pro 执行，reasoning.effort 则控制模型在该模式下投入多少推理。如果省略 reasoning.effort，GPT-5.6 在两种模式下都默认使用 medium。GPT-6.1 Sol、GPT-6 Sol 和 GPT-6 Luna 的默认推理强度也为 medium。

推理的工作原理

除了输入和输出 token，推理模型还使用推理 token。模型用这些 token 拆解提示词，并考虑多种回答方式。gpt-5.5 和 gpt-5.4 等推理模型支持交错推理：模型可以在开始推理前或各段推理之间生成可见输出，也可以在工具调用之间进行推理。

在多步对话中，早于 GPT-5.6 发布的模型默认沿用每一步的输入和输出 token，但不会把先前轮次的推理纳入下一次生成的上下文。GPT-5.6 模型默认会纳入先前轮次中可用的推理。对于支持的模型，可通过 reasoning.context 选择其一。

API 不显示推理 token，但这些 token 仍会占用模型的上下文窗口，并按输出 token计费。

控制成本

使用推理模型时，可以通过 max_output_tokens 参数限制生成的 token 总数，以控制成本。总数包括推理 token、可见的输出 token 和不可见的格式 token。生成的 token 如何计入用量和输出上限，详见输出 token 计数。

管理上下文窗口

创建响应时，要确保上下文窗口为推理 token 留出足够空间。视问题而定，模型可能生成几百到几万个推理 token。实际用量可在响应对象的 usage 字段中查看，具体位于 output_tokens_details 下：

为推理预留空间

如果生成的 token 数达到上下文窗口上限，或达到你设置的 max_output_tokens，响应的 status 会为 incomplete，且 incomplete_details 中的 reason 为 max_output_tokens。这可能发生在产生任何可见输出前，因此即使没有收到可见回复，也可能需要为输入和推理 token 付费。

为避免这一情况，请确保上下文窗口有足够空间，或调高 max_output_tokens。刚开始试用时，OpenAI 建议为推理和输出合计预留至少 25,000 个 token。了解自己的提示词需要多少推理 token 后，可以相应调整预留空间。

跨调用保留推理状态

对话状态和推理状态的用途不同。跨调用传递消息可以让模型获得可见的对话历史。对支持此功能的模型，保留推理状态还能将先前轮次中兼容的推理项纳入下一次生成的上下文。

保留推理状态可以延续推理，但不会公开模型原始的推理过程。推理项的内容不可见，API 不会返回其中的推理文本。可以通过 reasoning.context 控制模型能使用哪些已有的推理项：

GPT-5.6 模型系列支持 all_turns，并默认使用此值。更早的模型默认为 current_turn。GPT-6.1 Sol 也支持 all_turns。省略 reasoning.context 或设为 auto，即可使用所选模型的默认设置。

取值 行为
auto 使用所选模型的默认设置。省略 reasoning.context 与设为 auto 效果相同。
current_turn 允许使用当前轮次的推理，但不会将之前轮次的推理纳入下一次生成的上下文。
all_turns 将先前轮次中可用且兼容的推理项纳入下一次生成的上下文。GPT-5.6 模型和 GPT-6.1 Sol 支持此值。

响应的 reasoning.context 字段给出实际生效的模式：current_turn 或 all_turns。检查每个响应的该字段，即可确认模型使用了哪种模式。这项设置只使用已有的推理项，不会创建新项。

只有当请求能访问先前的响应项时，all_turns 才会生效。可以使用 previous_response_id、将响应关联到对话，或手动重新传入完整的响应历史。首次请求没有先前的推理，因此两种模式的行为相同。

保留的推理只能在同一模型系列内复用。例如，gpt-5.6-sol、gpt-5.6-terra 和 gpt-5.6-luna 可以复用彼此的推理，但 GPT-5.6 与 GPT-5.5 系列之间不能沿用推理。

切换模型系列时，即使 reasoning.context 为 all_turns，API 也不会将不兼容的推理纳入模型上下文。

在上下文中保留推理项

在 Responses API 中使用推理模型进行函数调用时，除了回传函数输出，强烈建议一并回传最近一次函数调用随附的所有推理项。如果模型连续调用多个函数，应回传自最近一条 user 消息以来的所有推理项、函数调用项和函数调用输出项。这样模型可以延续推理，用更少的 token 取得更好的结果。

最简单的做法是把上一个响应中的所有推理项传给下一次请求。系统会自动忽略与函数无关的推理项，只在上下文中保留相关项。可以使用 previous_response_id 参数传递先前响应中的推理项，也可以将先前响应的所有 output 项放入新请求的 input 中。

如果需要在发起下一次请求前截短并优化部分上下文，请确保最近一条用户消息与函数调用输出之间的所有项都原样传入下一次请求，让模型获得所需的完整上下文。

如需手动管理上下文，请参阅对话状态指南。

在对话中途调整推理设置

使用 configuration_update 可以在处理困难任务时调高推理强度，在处理常规后续问题时调低强度。在两次响应之间添加更新，同时保持请求级的 reasoning.effort 不变。这样可以保留原始提示词前缀，用于提示词缓存。

对于支持此功能的 GPT-6 及后续模型，可以在标准的单智能体模式下更新推理强度和响应格式。

在 HTTP Responses 请求或 WebSocket response.create 请求的 input 数组中，将下面这项放在下一条用户消息之前：

123456{
  "type": "configuration_update",
  "reasoning": {
    "effort": "high"
  }
}

推理摘要

API 不公开模型生成的原始推理 token，但可以用 summary 参数查看推理摘要。哪些模型支持摘要，详见模型文档。

phase 参数

通过 Responses API 使用 GPT-5.5 或 GPT-5.4 时，如果工作流运行时间较长或频繁调用工具，请使用助手消息的 phase 字段，避免模型过早停止或出现其他异常。 API 不强制要求 phase，但 OpenAI 建议使用它。对于助手的中途更新（如调用工具前的简短说明），请使用 phase: "commentary"；最终答案请使用 phase: "final_answer"。不要在用户消息中添加 phase。 使用 previous_response_id 通常最简单，因为它会保留助手先前的状态。如果手动传回助手的历史消息，请保留每条消息原有的 phase 值。 如果 phase 缺失或被丢弃，开场说明可能会被当作最终答案。针对特定模型的建议，详见GPT-5.5 提示词指南。

提示词编写建议

为推理模型编写提示词时，给能推理的 GPT-5 模型清晰的目标、明确的约束和输出要求通常最有效，不必规定每个中间步骤。

  • 告诉模型任务是什么、有哪些约束，以及应采用什么输出格式。
  • 把 reasoning.effort 当作调优参数，不要把它当作质量不佳时的主要补救手段。
  • 对于由智能体执行或需要大量研究的工作流，请明确任务的完成标准，以及模型应如何验证结果。

更多建议请参阅推理最佳实践。
