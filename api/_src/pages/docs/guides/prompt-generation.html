可以让 NexusVAI API 根据任务说明起草提示词和 JSON Schema，再由你审核、运行样例并修订。下方使用普通文本生成与结构化输出，不需要专门的提示词编辑器。

概览

将需求、输入和评价标准写成给模型的元提示词。它生成的是草稿，而非已经通过测试的配置。保留原始需求和典型输入，便于比较不同版本。

提示词

元提示词

说明新提示词的使用对象、输入格式、边界和期望结果。可将下方模板作为 instructions，将实际任务描述放进 input；调用方式见文本生成。

根据用户提供的任务草拟一条系统指令。写明目标、输入约束、输出格式和信息不足时的处理方式。把需要业务方确认的条件列在单独一段，不要补造事实。
根据给定语音场景，起草简短的对话指令。写明语气、确认关键信息的方式、被打断后的恢复和转交后端的条件。不要假定工具已执行或用户听清了回复。

编辑提示词

提供旧提示词、已观察到的失败样例以及必须保留的规则。让模型标记改动之处，再在同一组样例上比较新旧版本。

生成 Schema

先列出字段的含义、类型和必须出现的条件，让模型起草 Schema。接口中的字段放置位置见结构化输出示例及函数工具示例。

定义受约束的元 Schema

让模型先返回易于检查的字段清单：名称、类型、说明、是否必填。应用再将清单转为它支持的 Schema 表达，避免把生成结果直接投入生产。

清理输出

检查是否遗漏必填字段、是否允许意外属性，以及枚举和值域是否符合预期。用合法样例和应拒绝的反例分别测试。

元 Schema

元 Schema 描述 Schema 本身的结构。它能帮助程序先拒绝不合规的初稿，但不能验证字段含义或业务逻辑；这些仍需人工评审和测试。

只需描述任务，就可以用 Playground 中的生成按钮生成提示词、函数和 schema。本指南将介绍这个按钮的工作原理。

概览

从头编写提示词和 schema 可能很费时，使用生成功能可以更快上手。“生成”按钮主要采用两种方法：

  1. 提示词：我们将最佳实践融入元提示词，用它们来生成或改进提示词。
  2. Schema：我们使用元 schema 生成符合语法要求的 JSON 和函数定义。

目前我们使用元提示词和元 schema，今后可能会引入更先进的技术，例如 DSPy 和“梯度下降”。

提示词

元提示词指导模型根据任务描述编写高质量的提示词，或改进已有的提示词。Playground 中的元提示词借鉴了提示词工程的最佳实践，以及与用户合作积累的经验。

针对音频等不同输出类型，我们使用专门的元提示词，确保生成的提示词符合预期格式。

    ],
  });

生成 Schema

结构化输出的 schema 和函数 schema 本身都是 JSON 对象，因此可以用结构化输出来生成它们。 这需要先给预期输出定义一个 schema，而这里的输出本身也是 schema。为此，我们使用一种可以描述 schema 的定义，即元 schema。

函数 schema 中的 parameters 字段本身就是 schema，因此我们也用同一个元 schema 来生成函数。

定义受约束的元 Schema

结构化输出支持两种工作模式：strict=true 和 strict=false。两者使用同一个经过训练、能够遵循 schema 的模型，但只有严格模式能通过约束采样保证输出完全符合给定的 schema。

我们的目标是用严格模式自身生成符合严格模式的 schema。然而，JSON Schema 规范提供的官方元 schema 依赖严格模式暂不支持的特性。这同时给输入和输出带来了困难：

  1. 输入 schema：不能用严格模式不支持的特性描述输出 schema。
  2. 输出 schema：生成的 schema 不得包含严格模式不支持的特性。

为了在输出 schema 中生成新的键，输入元 schema 必须使用 additionalProperties。因此，目前不能直接用严格模式生成 schema，但我们仍希望生成结果符合严格模式的约束。

为克服这项限制，我们定义了伪元 schema。它使用严格模式不支持的特性，却只描述严格模式支持的特性。这样就可以在严格模式之外定义元 schema，同时确保生成的 schema 符合严格模式的约束。

我们如何设计伪元 schema

构建受约束的元 schema 并不容易，所以我们借助模型来完成。

我们先参考结构化输出文档，在 JSON 模式下向 o1-preview 和 gpt-4o 说明目标。经过几轮迭代，得到了第一个可用的元 schema。

接着，我们使用 gpt-4o 的结构化输出功能，将初始 schema 连同任务描述和文档一起交给模型，生成更好的候选方案。每轮都使用上一轮改进的 schema 生成下一版，最后进行人工审查。

清理输出后，我们用一组针对 schema 和函数的评测来验证结果。

清理输出

严格模式可以保证输出完全符合给定的 schema。但生成过程中无法使用严格模式，因此需要在生成后验证并转换输出。

生成 schema 后，执行以下步骤：

  1. 对所有对象，将 additionalProperties 设为 false。
  2. 将所有属性标记为必填项。
  3. 对于结构化输出的 schema，将其封装在 json_schema 对象中。
  4. 对于函数，将其封装在 function 对象中。

Realtime API 的 function 对象与 Chat Completions API 的对应对象略有不同，但两者使用相同的 schema。

每个元 schema 都有一条包含少样本示例的提示词。借助这些提示词和结构化输出本身的可靠性，即使不使用严格模式，也能生成 schema。

def generate_schema(description: str):
    messages = [
        {"role": "system", "content": META_PROMPT},
        {"role": "user", "content": "Description:\n" + description},
    ]
    validator = Draft202012Validator(META_SCHEMA["schema"])
    # Generation is non-strict. Validate locally and allow one correction.
    for attempt in range(2):
        completion = client.chat.completions.create(
            model="gpt-5.6-terra",
            response_format={"type": "json_schema", "json_schema": META_SCHEMA},
            messages=messages,
        )
        choice = completion.choices[0]
        if choice.finish_reason != "stop" or choice.message.refusal:
            raise ValueError("Schema generation did not complete successfully")
        content = choice.message.content
        schema = json.loads(content)
        try:
            validator.validate(schema)
        except ValidationError as error:
            if attempt == 1:
                raise
            messages.extend(
                [
                    {"role": "assistant", "content": content},
                    {
                        "role": "user",
                        "content": (
                            "Correct the schema to satisfy the original meta-schema. "
                            f"Validation error at {error.json_path}: {error.message}. "
                            "Return only the corrected JSON."
                        ),
                    },
                ]
            )
        else:
            return schema
