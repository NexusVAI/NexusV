用 NexusVAI API 提取字段或返回分类结果时，可以在请求中指定 JSON Schema。是否支持该格式、是否严格遵循 Schema 取决于所选模型；应用必须处理拒答、截断、解析失败与业务规则不满足的情况。

支持的模型

从模型目录选择模型，用实际输入验证输出结构。不能仅凭模型支持文本生成，就假定它也支持所有 JSON Schema 特性。

结构化输出与 JSON 模式对比

json_schema 描述字段、类型和约束；json_object 只要求 JSON 对象，不约束业务结构。两者都需要在应用端检查结果。

示例

下面从短句中提取人名和城市。两种协议使用不同的字段，不能把其中一种请求体直接交给另一种端点。

通过 text.format 使用结构化输出

在 Responses 的 text.format 中指定 name 与 schema，从响应正文读取 JSON。

{
  "model": "gpt-6-astra",
  "input": "提取人名和城市：小王上周去了杭州。",
  "text": {"format": {
    "type": "json_schema",
    "name": "extraction",
    "strict": true,
    "schema": {
      "type": "object",
      "properties": {"name": {"type": "string"}, "city": {"type": "string"}},
      "required": ["name", "city"],
      "additionalProperties": false
    }
  }}
}

何时用函数调用，何时用 text.format

只需把模型回复交给程序解析时，用 text.format；需要让模型请求由你的应用执行某项操作时，用函数工具，并验证参数后再执行。

通过 response_format 使用结构化输出

在 Chat Completions 的 response_format.json_schema 下指定同样的 Schema，从助手消息读取结果。

{
  "model": "gpt-6-astra",
  "messages": [{"role": "user", "content": "提取人名和城市：小王上周去了杭州。"}],
  "response_format": {"type": "json_schema", "json_schema": {
    "name": "extraction",
    "strict": true,
    "schema": {
      "type": "object",
      "properties": {"name": {"type": "string"}, "city": {"type": "string"}},
      "required": ["name", "city"],
      "additionalProperties": false
    }
  }}
}

何时用函数调用，何时用 response_format

结构化回复供应用解析；函数调用请求应用使用具体工具。不要把一个结构看似正确的回复直接当成操作授权。

流式输出

增量片段可能还不是可解析的 JSON。先累积完整文本并检查结束状态，再解析和校验。有关事件和错误，见 Responses 流式输出或 Chat Completions 流式输出。

支持的 Schema

为可移植性，从一个简单的 object、明确的 properties、required 和 additionalProperties 开始。用代表性输入测试空值、枚举、嵌套以及额外字段。

模型与关键字限制

不是所有模型都实现同样的关键字与限制。额外的业务规则（日期范围、字段之间的关系等）在应用代码中校验，不要依赖网关强制执行所有约束。

JSON 模式

只需合法 JSON 对象时，在支持的模型上用 {"type":"json_object"}，并在提示词中明确要求输出 JSON。仍需校验字段，异常或不完整的输出不要交给后续操作。

JSON 是全世界应用之间交换数据最常用的格式之一。

结构化输出（Structured Outputs）是一项确保模型始终按你提供的 JSON Schema 生成响应的功能，你不用再担心模型漏掉必填键，或虚构一个不合法的枚举值。

结构化输出的好处包括：

  1. 可靠的类型安全：无需再验证或重试格式错误的响应
  2. 可检测的拒答：因安全原因导致的拒答可以用代码识别
  3. 提示词更简单：不必再靠措辞强硬的提示词来固定格式

支持的模型

我们最新的大语言模型都支持结构化输出，从 GPT-4o 开始。新项目建议从 gpt-6-astra 起步。gpt-4-turbo 及更早的旧模型可改用 JSON 模式。

何时用 function calling，何时用 response_format

何时用 function calling，何时用 text.format

在 OpenAI API 中，结构化输出有两种使用方式：

  1. 配合 function calling 使用
  2. 使用 json_schema 响应格式

当你要构建一个连接模型与应用自身功能的程序时，适合用 function calling。

例如，你可以让模型访问查询数据库的函数，做一个能帮用户查订单的 AI 助手，或者让函数与 UI 交互。

反过来，通过 response_format 使用的结构化输出，更适合「模型给用户回话时要遵守某个 schema」的场景，而不是模型调工具时的场景。

例如你在做一个数学辅导应用，想让助手按特定 JSON Schema 回复用户，好让你生成的 UI 用不同方式展示模型输出的各个部分。

实践中：

  • 如果你要把模型接到系统里的工具、函数、数据等之上，就用 function calling——如果你想规范模型回给用户看的那段输出的结构，就用结构化的 response_format
  • 如果你要把模型接到系统里的工具、函数、数据等之上，就用 function calling——如果你想规范模型回给用户看的那段输出的结构，就用结构化的 text.format

结构化输出与 JSON 模式对比

结构化输出是 JSON 模式的升级版：两者都保证输出是合法 JSON，但只有结构化输出能保证它符合你给的 schema。Responses API、Chat Completions API、Assistants API、Fine-tuning API 和 Batch API 都支持结构化输出与 JSON 模式。

能用结构化输出时，我们建议始终用它代替 JSON 模式。

不过，response_format: {type: "json_schema", ...} 形式的结构化输出仅在 gpt-4o-mini、gpt-4o-mini-2024-07-18、gpt-4o-2024-08-06 及之后的模型快照上受支持。

通过 response_format 使用结构化输出

你可以用 SDK 提供的辅助方法把模型输出解析成目标格式，也可以直接指定 JSON schema。

注意：对微调模型，你用某个 schema 发的第一个请求会因 API 处理 schema 而多出一点延迟，之后用同一 schema 的请求不再有此延迟。其他模型没有这个限制。

SDK 对象
第一步：定义对象

首先要定义一个对象或数据结构，表示模型必须遵循的 JSON Schema。可参考本指南开头的示例。

结构化输出支持 JSON Schema 的大部分特性，但有些出于性能或技术原因不可用，详见这里。

例如，你可以这样定义对象：

from pydantic import BaseModel


class Step(BaseModel):
    explanation: str
    output: str


class MathResponse(BaseModel):
    steps: list[Step]
    final_answer: str
import { z } from "zod";
import { zodResponseFormat } from "openai/helpers/zod";

const Step = z.object({
  explanation: z.string(),
  output: z.string(),
});

const MathResponse = z.object({
  steps: z.array(Step),
  final_answer: z.string(),
});

数据结构建议

为了尽量提高模型输出质量，我们建议：

  • 给键取清晰、直观的名字
  • 为结构中的重要键写清 title 和 description
  • 建立并使用 evals 来确定最适合你场景的结构

提示与最佳实践

处理用户生成的输入

如果你的应用使用用户输入，请在提示词中说明当输入无法得到有效响应时该怎么办。

模型总会尽力遵守给定 schema——当输入与 schema 完全无关时，这可能反而造成幻觉。

你可以在提示词里写明：如果模型判断输入与任务不匹配，就返回空参数，或返回一句特定的话。

处理错误

结构化输出仍然可能出错。发现错误时，可以调整指令、在 system 指令中给示例，或把任务拆成更简单的子任务。更多调教输入的方法见提示词工程指南。

避免 JSON schema 漂移

为防止 JSON Schema 与代码中对应的类型定义逐渐不一致，我们强烈建议在可用时使用 SDK 自带的 schema 辅助方法。

如果你更愿意手写 JSON schema，可以加 CI 规则在 schema 或底层数据对象被改动时报警，或加一个从类型定义自动生成 JSON Schema（或反向）的 CI 步骤。

流式输出

你可以用流式方式在模型响应或函数调用参数生成的同时处理它们，并解析成结构化数据。

这样就不必等整个响应完成再处理。如果想逐个显示 JSON 字段，或在函数调用参数一出来就处理它，这特别有用。

我们建议依赖 SDK 来处理结构化输出的流式解析。

不使用 SDK 的 stream 辅助方法也能流式处理函数调用参数，示例见 function calling 指南。

支持的 schema

结构化输出支持 JSON Schema 语言的一个子集。

支持的类型

结构化输出支持以下类型：

  • String
  • Number
  • Boolean
  • Integer
  • Object
  • Array
  • Enum
  • anyOf

支持的属性

除了指定属性类型外，你还可以指定一组额外约束：

支持的 string 属性：

  • pattern — 字符串必须匹配的正则表达式。
  • format — 预定义的字符串格式。当前支持：
    • date-time
    • time
    • date
    • duration
    • email
    • hostname
    • ipv4
    • ipv6
    • uuid

支持的 number 属性：

  • multipleOf — 数值必须是该值的倍数。
  • maximum — 数值必须小于等于该值。
  • exclusiveMaximum — 数值必须小于该值。
  • minimum — 数值必须大于等于该值。
  • exclusiveMinimum — 数值必须大于该值。

支持的 array 属性：

  • minItems — 数组至少包含这么多项。
  • maxItems — 数组最多包含这么多项。

对象的嵌套深度与规模有限制

一个 schema 最多可有 5000 个对象属性，嵌套最多 10 层。

字符串总长度限制

一个 schema 中，所有属性名、定义名、枚举值与 const 值的字符串总长度不能超过 120,000 字符。

枚举规模限制

一个 schema 中所有枚举属性合计最多 1000 个枚举值。

当某个字符串枚举属性的枚举值超过 250 个时，所有枚举值的字符串总长度不能超过 15,000 字符。

JSON 模式

JSON 模式是结构化输出的基础版本。JSON 模式只保证输出是合法 JSON，结构化输出则能可靠地把模型输出约束到你指定的 schema。只要场景支持，我们建议用结构化输出。

开启 JSON 模式后，模型输出保证是合法 JSON——除了少数需要你自行检测并妥善处理的边界情况。

在 Chat Completions 中开启 JSON 模式：把 response_format 设为 { "type": "json_object" }。使用 function calling 时 JSON 模式始终开启。

在 Responses API 中开启 JSON 模式：把 text.format 设为 { "type": "json_object" }。使用 function calling 时 JSON 模式始终开启。

注意事项：

  • 使用 JSON 模式时，你必须在会话中通过某条消息（如 system 消息）明确要求模型输出 JSON。若缺少明确的生成 JSON 指令，模型可能输出无限长的空白流，请求会一直跑到 token 上限。为防止忘记，只要上下文中没有出现字符串 “JSON”，API 会直接报错。
  • JSON 模式不保证输出符合任何特定 schema，只保证它合法且能正常解析。要保证符合你的 schema 请用结构化输出；用不了的话，就改用校验库并加重试来兜住输出。
  • 你的应用必须检测并处理那些会导致输出不是完整 JSON 对象的边界情况（见下文）。
