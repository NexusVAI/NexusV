语音智能体让用户通过说话向你的应用提问并完成任务。关键的设计选择是语音如何与推理和工具连接：可以是与独立后端持续对话、使用单一语音模型，或由你逐环节控制的流水线。

选择合适的架构

架构 适用场景 选择理由
GPT-Live 与独立后端配合的全双工对话 保留现有文本工作流，并在对话持续进行时独立选择它的后端。
Realtime API 在一个会话中完成语音、推理和工具调用 由一个模型理解音频、决定下一步并以语音回应。
串联式语音流水线 可以控制语音和文本的每个环节 可以检查或转换中间文本，并独立替换每个组件。

构建全双工语音智能体

GPT-Live 可以同时听和说，这种能力称为全双工。实时模型负责语音交互，并把推理和工具调用委托给独立的后端。后端工作运行时，用户仍可继续说话。

你可以保留现有的文本工作流，包括其业务逻辑和工具，再把 GPT-Live 作为语音界面接入。委托模式决定由谁执行后端工作，以及由谁提供对话上下文：

  • 客户端委托：接入你自己的智能体或工作流，后端模型和服务商由你选择。应用执行这些工作，并把结果返回给 GPT-Live。
  • Responses 委托：选择 OpenAI 托管的 Responses 模型负责后端推理和工具调用。GPT-Live 提供对话上下文并管理对该模型的调用；自定义函数仍由你的应用执行。

两种模式下，权限和业务记录都由你的应用控制。说话方式写在实时模型的提示词中，业务规则写在后端提示词中。

先阅读 GPT-Live 入门。后端配置见委托与工具，说话方式见语音模型提示词。

构建语音到语音的智能体

对于 Realtime API，RealtimeAgent 和 RealtimeSession 提供了面向浏览器的起点。会话负责处理音频轮次、工具、打断和交接。完整示例已移至 Realtime API 入门。

构建串联式语音工作流

当你需要在语音识别、智能体和语音生成之间检查或转换文本时，使用串联路径。你的应用负责三个环节：

  1. 语音转文字
  2. 智能体工作流本身
  3. 文字转语音
import asyncio
import numpy as np

from agents import Agent, function_tool
from agents.voice import AudioInput, SingleAgentVoiceWorkflow, VoicePipeline


@function_tool
def get_weather(city: str) -> str:
    """Get the weather for a given city."""
    return f"The weather in {city} is sunny."


agent = Agent(
    name="Assistant",
    instructions="You are a helpful voice assistant.",
    model="gpt-6-astra",
    tools=[get_weather],
)


async def main() -> None:
    pipeline = VoicePipeline(workflow=SingleAgentVoiceWorkflow(agent))
    audio_input = AudioInput(buffer=np.zeros(24000 * 3, dtype=np.int16))
    result = await pipeline.run(audio_input)
    async for event in result.stream():
        if event.type == "voice_stream_event_audio":
            print("Received audio bytes", event.data.nbytes)


if __name__ == "__main__":
    asyncio.run(main())

当每个环节都需要可见或可替换时，使用这条路径。例如，你可以保存转写文本，在文本智能体回答前执行策略检查，调用内部系统，并且只在工作流得出获准的回答后才生成语音。

评估语音智能体

对话和最终完成的任务都要测试。以预约助手为例，要听取它的确认语，并检查正确的预约是否已保存。

  1. 选取有代表性的场景，并写明预期结果、工具调用和权限。
  2. 保存验证每个结果所需的音频、事件、工具结果和应用状态。要区分评估运行本身失败，与运行有效但智能体未完成任务这两种情况。
  3. 重复运行场景，比较任务完成情况、可听到的响应延迟、打断和不必要的静默。比较改动时，保持调用方、模型配置、工具和传输方式一致。

对于 GPT-Live，以下几个维度要分别测量：

  • 任务和工具结果：检查用户意图是否被保留、委托的工作、工具参数、权限和最终应用状态。核对语音确认的内容与实际完成的操作是否一致。
  • 对话节奏：测量可听到的响应时间、不必要的静默、重叠，以及被打断时的让步，包括后端工作运行时用户的更正。
  • 语音与语言：测试不同口音、背景噪声、语言切换、人名和数字下的输入识别。输出的清晰度和语言选择要与识别效果分开评估。
  • 会话可靠性：把连接失败、音频丢失、超时和未完成的会话与任务分数分开统计。

按爬、走、跑三个阶段逐步增加复杂度：

  1. 爬：用合成语音发起受控的单轮请求。保持生成的音频、应用上下文和预期结果不变，以便重复比较。
  2. 走：回放有代表性的真人单轮请求录音，测试声音、麦克风、停顿和声学环境如何影响表现。
  3. 跑：使用独立的模拟用户进行连续的多轮对话。测试对话与后端工作重叠时的澄清、需求变化、打断和恢复。

自动评分之外，还要由人工听取来评估发音、自然度，以及对话节奏是否合适。

GPT-Live 的评估框架见 语音智能体评估 Cookbook。

Realtime 的评估框架和完整示例，请参阅 OpenAI Cookbook 中的 Realtime 评估指南。

测量延迟

测量调用方等待一个有用的语音回答要多久。后端耗时要单独统计以定位延迟，并比较相似通话的中位数和第 95 百分位数。

比较前端模型时，要保持调用方、录音、后端模型、提示词、传输方式、音频节奏和评分器不变。

对于 GPT-Live，记录应用能观察到的各个阶段：收到委托、后端请求开始、第一个有用结果、工具开始和结束、提交结果、音频到达和客户端播放。客户端委托让你的应用直接看到它发出的后端请求；Responses 委托会暴露嵌套的响应事件，以及你的应用执行的自定义工具。

用这些时间点定位连接建立、模型处理、工具、缓冲或播放中的延迟。“我正在查”之类的确认语要与调用方真正需要的答案分开测量。

每次只改动一个因素，并重复相同的场景。检查响应变快是否也影响任务成功率、工具调用的正确性或打断处理。参见降低后端延迟。

语音智能体仍然使用相同的核心智能体构件

语音界面改变的是传输和音频循环，核心的工作流决策并没有变化：

  • 当语音智能体需要外部能力时，参阅使用工具。
  • 当语音工作流需要流式输出、续接或持久状态时，参阅运行智能体。
  • 当语音工作流需要在多个专职智能体之间分支时，参阅编排与交接。
  • 当语音工作流需要安全检查或审批时，参阅护栏与人工复核。
  • 当你需要由 MCP 提供的能力，或想检查语音工作流的运行情况时，参阅集成与可观测性。

实用原则是：先选定音频架构，再像设计文本智能体那样设计其余的工作流。
